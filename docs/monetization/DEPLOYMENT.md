# Meldiq Plus deployment and migration

This candidate changes new Meldiq Plus purchases to **499 USD cents per month, 1,299 cents every three months, or 4,999 cents every twelve months**. The later scope correction preserves Bots+, Sparks and other existing products. Go remains discontinued. New paid Plus offers and marketing campaigns remain unpublished until the provider compatibility matrix is complete. Existing agreements are never repriced. Code publication is separately authorized by the user.

The server source is the isolated `codex/plus-monetization-20261102` worktree under `meldiq_android/.claude/worktrees/plus-monetization-20261102`, integrated with production media `b34d3ee8` and read receipts `0f77a9d8`. The release web worktree includes current main's call photos, RTT, seen receipts and compact sidebar. Use the exact sources recorded in the production receipt; never package the unrelated dirty shared checkout. The administrator source is `meldiq_central_admin`.

## Catalog and provider transition

`server/src/modules/billing/pricing.ts` defines Meldiq Free at 0 and Meldiq Plus with approved USD recurring terms (499 monthly; 1,299 every three months; 4,999 yearly), pricing version `2026-11-02.plus-terms-v3`, effective from 2 November 2026 at 00:00 Asia/Shanghai. Public billing configuration includes the provider environment and product/plan identifiers. The main comparison remains Free and Meldiq Plus. Checkout offers the interval choices and shows the full recurring charge. Three months saves 198 cents (13.23%); twelve months saves 989 cents (16.52%) against repeated monthly billing. Equivalent monthly figures are rounded explanatory values, never installment amounts. Payment supports infrastructure and development; no unverifiable spending allocation or survival guarantee is displayed.

New personal Plus checkout, gifts and card subscription quotes require the approved current price. PayPal verifies the actual remote plan's currency, approved interval/frequency, amount, quantity, tax/setup fee and optional product ID before creating a subscription. The browser supplies product/recipient/request identifiers, never authoritative prices. Stored quotes remain authoritative for an already-created purchase; a changed quote requires review before approval.

Existing subscriptions retain their immutable plan version, original amount, provider subscription/customer references, dates and history. PayPal reconciliation maps each historical PayPal plan ID to its published stored amount, including retired versions. Google Play reconciliation retains the version for an existing unchanged product. No plan-level pricing update or agreement revision API is called. New agreement creation requires buyer approval; keeping an existing agreement requires no new agreement.

PayPal currently documents that a plan-level price change also affects existing subscribers, with email notice and a ten-day window, and deferral when the next cycle falls within that window. This implementation avoids that operation. Any future repricing requires a separate review of affected customers, applicable consent, required notices and effective dates. See [PayPal plan pricing](https://developer.paypal.com/subscriptions/change-price), [subscriptions](https://developer.paypal.com/docs/subscriptions/), [webhook verification](https://developer.paypal.com/api/webhooks/v1), and [idempotency](https://developer.paypal.com/api/rest/reference/idempotency/).

The read-only `/admin/v1/billing/pricing-migration` endpoint groups subscriptions by original plan/version/amount/provider plan/status and counts gifts and pending checkouts. Run it in the actual deployment before publication; this candidate has not read production customer records. The public pre-change catalog snapshot is stored separately and shows the old live 399-cent offer; it is not a customer inventory.

The exact non-secret IDs are in `sandbox-plan.json`, `sandbox-quarterly.json` and `sandbox-yearly.json`. These are prepared provider resources; none were published to an application catalog. No buyer approval, capture, entitlement grant or live operation occurred. The pending subscription was not cancellable in that state. See `sandbox-verification.json`.

The available private Sandbox environment has no webhook ID. Complete buyer approval, real signed webhook delivery, paid activation, failed payment, renewal, suspension, cancellation, refund/reversal, gift redemption and duplicate-event delivery before release. Automated REST doubles cover the application boundaries but do not replace these provider checks.

Use `server/scripts/paypal-plus-v2-setup.ts` for the new resources. Select `--term=monthly`, `--term=quarterly` or `--term=yearly`. Its default is a dry run; `--execute` prepares resources without publishing billing or changing environment files. Live preparation additionally requires an explicit compatibility approval reference. Save returned v2 resource IDs privately and reuse them on later runs; provider request IDs only protect retries within PayPal's retention period. The old all-in-one setup scripts refuse execution to prevent accidentally recreating a 399-cent Plus offer. Existing unrelated checkout, subscription management, refund and webhook paths remain available.

## Promotions

Campaigns and interruptive popups default off. Settings live in the existing billing database. Only verified, onboarded Free accounts qualify; administrators/test accounts, active Plus and active checkouts are excluded. Defaults require three days of account age and three meaningful sessions across two days. Meaningful activity uses coarse first-party session timing, with a minimum of sixty active seconds, no content analysis or fingerprinting.

Across campaigns and devices: at most one popup and three total impressions in a rolling thirty days; one impression per session; at least seven days between impressions; fourteen days after dismissal; thirty days after snooze. Configuration can tighten these safety limits. Reservations consume allowance before rendering; analytics distinguish reservations from confirmed presentation. MongoDB revision checks reject competing stale reservations transactionally. Deterministic account/campaign hashing assigns optional A/B variants.

Web and Android use the same claim/feedback/preference API. They fail closed when eligibility or persistence is unavailable. Calls, screen sharing, recording/composition, transfers, dialogs, errors, checkout, authentication/onboarding and critical settings suppress presentation by restricting it to a settled Home surface. Web downloads share the existing communication-busy hold; conversion/storage implementation is unchanged. Displayed promotions recheck server state every five seconds and expire without a successful refresh. The kill switch prevents new reservations immediately; open presentations withdraw at the next successful check or ten-second expiry. Network delivery cannot provide an instantaneous remote UI change.

The console adds campaign activity, copy, image path, target/usage requirements, triggers, presentation, frequency/cooldowns, schedules/regions, CTA, controlled experiments, preview, guardrail metrics, and a global disable action. Changes reuse billing permissions, fresh passkey verification, revision guards and the hash-chained audit. Campaigns cannot override subscription pricing. Region-scoped campaigns stay suppressed when a trusted region is unavailable. Advanced fields use validated JSON in the console.

Guardrails include dismissals, repeated dismissals, opt-outs, complaints, confirmed impressions, clicks, pricing visits, checkout starts, attributed conversions/cancellations/refunds and experiment counts. Checkout abandonment is a coarse difference between attributed checkout starts and conversions, not an individual funnel or retention study. No statistical optimization is enabled automatically.

Billing reminders are separate from promotional campaigns. During the last 72 hours of verified Plus access, the server reserves one informational notice per account/agreement/end-date across devices. An auto-renewing agreement shows its existing amount and cadence plus Manage billing; it never asks for a second subscription. Canceled renewals and ending gift/trial grants receive expiry wording. Google Play notices defer the exact localized charge to Play. Renewal email uses the existing durable outbox and is deduplicated per billing period. This transactional information is not controlled by the marketing popup switch.

## Database and rollback

Migration 093 adds `billing_promotion_settings`, `billing_promotion_state`, and `billing_promotion_events`, with indexes. The existing migration ledger makes application idempotent. Migration 094 adds billing frequency with a default of one to historical versions and freezes it after publication. MongoDB backfills missing frequency metadata before applying the new validator. MongoDB schema version is 10; the billing domain retains the existing database architecture. Financial, gift, customer and grant records are not rewritten or deleted. Existing promotion-code and gift-administration functions remain in their original module; upgrade discovery is in `upgradePromotions.ts`.

Before applying anything, confirm migration/version numbers against the newest integrated source, acquire the existing release lock, take the current encrypted database/attachment backup, verify an isolated restore, and preserve a compatible fallback. Create/validate the new collections and indexes with the deployment's existing migration process and appropriate schema privileges. Do not switch database authority or storage adapters.

For rollback, first disable campaigns and make new Plus offers non-public while keeping the provider, verified webhooks and existing agreements operational. Use a fallback that understands 399-, 499-, 1,299- and 4,999-cent agreements with their original cadence and the current schema. An older adapter that accepts only 399 cents is unsafe after new purchases. Do not drop collections, delete financial history, rewrite customer agreements, or restore an older data snapshot over new transactions as an ordinary rollback.

## Release gates

1. Integrate current production sources, including attachment publication migration 092. Plus migrations remain additive at 093 and 094 (MongoDB schema 10).
2. Finish the account-level migration inventory and verified backup/restore; preserve all provider references and history.
3. Validate the frozen release source and record exact test results and artifact hashes. The production web artifact must come from the checked GitHub Actions Node 22 build. Do not compile or run the full test suite on the VPS.
4. Code/schema rollout may proceed with new Plus offers withheld and campaigns off. Before publishing paid offers, complete the real Sandbox buyer and webhook matrix above, and validate guest/card eligibility without collecting raw card data.
5. Prepare distinct live product/plan IDs and verify all approved remote amounts and cadences. Obtain the compatibility/release approval before publication. Do not update a live plan's pricing scheme.
6. Keep existing other-product settings unchanged. Configure the reviewed new Plus IDs and publish a new immutable version with `billing-paypal-plus --term=<monthly|quarterly|yearly> --publish` through the existing operator process. Record the audit/reference and verify public catalog/checkout against the provider.
7. Verify authenticated web billing/gifts/history, unchanged add-ons and legacy renewals before enabling campaigns. Enable a limited campaign only after safety and cross-device checks.
8. For Play-distributed Android builds, configure and verify the approved Google Play product/base-plan prices. The UI continues through native Play billing; promotions do not send users to PayPal. Follow [Google Play Payments policy](https://support.google.com/googleplay/android-developer/answer/9858738) and any applicable enrolled exception. Signing, physical-device checks and store publication remain separate release steps.

## Guarded production cutover

Acquire both the global production lease and web deployment lock. Guard the current image and site paths. Snapshot account and financial-record digests privately, then route all 13 API ingress entries to the existing maintenance responder. Change only the Compose API image, keeping all environment values, mounts, ports, limits and other services. Verify schema 10 across all 16 database authorities, preserved accounts/financial records, healthy Redis, legacy billing access and exact served artifact hashes. Restore ingress configuration byte-for-byte after verification. Keep previous hashed assets for open tabs.

The compatible fallback contains the current production API plus the schema-10 migration/catalog metadata. It may be used only before new paid Plus terms are published. It preserves read receipts, media publication and all database authorities. It never downgrades the database or restores an old snapshot over new transactions. Never use this pre-publication fallback after accepting 499/1299/4999-cent Plus agreements.

The current production media ceiling is 1,000,000,000 bytes. Preserve the newer media release's decimal-gigabyte limit and client-side encryption, previews and retries.
