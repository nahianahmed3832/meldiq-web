# Bot voice implementation boundary

Active work following source checkpoint API445fac6f / Webf8ef1e4. No voice completion, production deployment or physical-device proof is claimed here. The broader platform remains in scope; recording, clips/buffers, soundboards and hosted execution remain explicitly deferred.

The released text-bot identity has no human account, session, device certificate or private identity key. Native call keys travel in encrypted device envelopes, so issuing an ordinary human media token cannot produce working encrypted bot participation. Do not manufacture a human device or expose a raw call key through the API.

1. Register only a bot-generated public X25519 media key in the existing requested manifest. Keep its private half in the bot process. Current manifest revision and explicit installation approval bind the key fingerprint; changing or clearing it withdraws media authority until fresh review. Native roles and voice bans still apply. The owner edits the public key in Developer; the manager sees its fingerprint and bot/developer listening disclosure before approval.
2. Add a separate `botvoice_` participant identity with a bounded, short-lived in-memory lease. It creates no account device, human session or user WebSocket grant. Use the existing Frankfurt calls/SFU paths and room capacity. Tokens are room-scoped, audio-only, with no data/metadata publishing. Connect and speak scopes are independent and intersect current native authority.
3. Start by joining an existing native voice-room call. Current connected human clients holding its key seal it to the approved bot public key with the existing HPKE suite, using call/channel/bot/lease/manifest-revision AAD. Relay only bounded ciphertext, in memory for the lease; no keys or submitted ciphertext in journals, durable drafts or logs. Subsequent work must cover bot initiation and native-client key handoff before the whole voice surface is accepted.
4. Renew leases with current bot credentials; verify actual SFU presence before recording a connection. Token rotation, uninstall, key/approval changes, native bans, timeout, lease expiry and deleted identities must evict the media participant. Reject old tokens on webhook admission. Retain/retry failed eviction work, and recover orphan bot participants on restart. Existing native mute/disconnect rules apply; destination moves stay deferred.
5. Keep BOT identity visible in call participants. Encryption badges continue to depend on verified encrypted frames. Never fall back to unencrypted media. A bot and its operator can process media it is approved to hear; this does not imply a Meldiq recording product.

Qualification requires actual local SFU peers with verified encrypted audio, private-key absence from API/storage/logs, authority/race/restart/expiry and capacity cases, Web keyboard/phone-width/RTL behavior, old/native additive decoding, Android source integration and the coordinated final staging/rollback checks. Native physical devices remain pending by explicit owner decision.
